## 一、风险管理框架

### 1.1 风险分类

- **技术风险**: 技术选型、架构设计、性能问题
- **进度风险**: 延期、人力不足、依赖阻塞
- **成本风险**: 预算超支、LLM成本失控
- **质量风险**: 功能缺陷、用户体验差、安全漏洞
- **外部风险**: 供应商变更、政策变化、竞争压力

### 1.2 风险等级定义

**概率**:
- 高（H）: >50%
- 中（M）: 20%-50%
- 低（L）: <20%

**影响**:
- 高（H）: 导致项目失败或核心功能无法交付
- 中（M）: 影响部分功能或进度延期1-2周
- 低（L）: 轻微影响，可快速恢复

**风险等级 = 概率 × 影响**:
- 🔴 高风险: HH, HM, MH
- 🟡 中风险: MM, HL, LH
- 🟢 低风险: ML, LM, LL

## 二、已识别风险清单

### 2.1 技术风险

**R-T01: LLM成本超支**
- **描述**: Claude API调用频繁，月成本超过¥2000预算
- **概率**: 高（H）
- **影响**: 高（H）
- **等级**: 🔴 高风险
- **触发条件**: 日均Token消耗>200K
- **应对策略**:
  1. **预防**:
     - LLM缓存命中率≥50%（Redis 1小时TTL）
     - Prompt优化，减少Token消耗20-30%
     - 简单问题模板回复（降级机制）
     - 每日配额限制（免费用户100次/天）
  2. **监控**:
     - 每日成本统计（llm_token_logs表）
     - 成本警报（超¥50/天触发邮件）
  3. **应急**:
     - 启用更激进的缓存策略（24小时TTL）
     - 降低免费用户配额至50次/天
     - 部分功能暂时禁用（直播脚本生成）
- **责任人**: 后端工程师

**R-T02: IP人格不稳定**
- **描述**: AI回复缺乏特色，IP特征词出现率<80%
- **概率**: 中（M）
- **影响**: 高（H）
- **等级**: 🔴 高风险
- **触发条件**: 用户反馈IP无特色
- **应对策略**:
  1. **预防**:
     - Prompt多轮测试（100条对话验证）
     - Few-shot Examples精心设计
     - 系统Prompt明确约束
  2. **监控**:
     - 抽样检查（每周100条对话）
     - 特征词自动检测
  3. **应急**:
     - Prompt快速迭代
     - 人工抽检并纠正
     - 引入用户反馈按钮
- **责任人**: AI工程师

**R-T03: 知识图谱查询性能差**
- **描述**: 溯源查询响应时间P95>2s
- **概率**: 中（M）
- **影响**: 中（M）
- **等级**: 🟡 中风险
- **触发条件**: 数据量>1000产品
- **应对策略**:
  1. **预防**:
     - 关键字段建立索引
     - 查询结果缓存（Redis）
  2. **优化**:
     - SQL查询优化（EXPLAIN分析）
     - 引入Neo4j（Phase 2）
  3. **降级**:
     - 返回部分数据
     - 异步加载文化元素详情
- **责任人**: 后端工程师

**R-T04: Claude API不稳定**
- **描述**: Anthropic API间歇性超时或503错误
- **概率**: 低（L）
- **影响**: 高（H）
- **等级**: 🟡 中风险
- **触发条件**: API错误率>5%
- **应对策略**:
  1. **预防**:
     - 超时设置（30s）
     - 指数退避重试（3次）
  2. **降级**:
     - 返回模板回复
     - 提示"AI暂时繁忙，请稍后重试"
  3. **备选方案**:
     - 准备文心一言API作为备份
- **责任人**: 后端工程师

## 三、风险监控机制

### 3.1 风险仪表板

**每周更新** (Excel/Notion):
| 风险ID | 风险名称 | 等级 | 状态 | 负责人 | 更新时间 |
|--------|---------|------|------|--------|---------|
| R-T01 | LLM成本超支 | 🔴 | 监控中 | 张三 | 2026-06-11 |
| R-S01 | Sprint 1延期 | 🔴 | 已触发 | 李四 | 2026-06-11 |

**状态定义**:
- 未发生: 风险未触发
- 监控中: 接近触发条件
- 已触发: 风险已发生，执行应对措施
- 已关闭: 风险已解决或不再适用

### 3.2 风险会议

**每周五下午3点** (30分钟):
1. 回顾本周风险状态
2. 识别新风险
3. 评估应对措施效果
4. 调整下周风险优先级

**参会人员**: 项目负责人、技术负责人、各模块负责人

### 3.3 风险指标

**关键指标**:
- LLM日均成本: ≤¥65/天
- Sprint进度: ≥90%完成
- 测试覆盖率: ≥60%
- 用户满意度: ≥4.0/5.0
- 系统可用性: ≥99%

**监控工具**:
- 成本: daily_cost_summary表
- 进度: JIRA燃尽图
- 质量: pytest-cov / Jest
- 可用性: Prometheus + Grafana

## 四、风险响应流程

### 4.1 风险触发流程

```
风险触发 → 通知负责人 → 评估影响 → 执行应对措施 → 跟踪结果 → 关闭风险
```

### 4.2 风险升级机制

**升级条件**:
- 🔴 高风险触发
- 应对措施无效（3天未改善）
- 影响范围扩大

**升级路径**:
```
模块负责人 → 项目负责人 → 指导老师
```

### 4.3 应急预案

**预案1: LLM成本失控**
```
Day 1: 启用24小时缓存 + 降低配额
Day 2: 禁用直播脚本生成功能
Day 3: 切换到文心一言API
```

**预案2: 关键成员缺席**
```
Day 1: 任务重新分配
Day 3: 启动外部支援流程
Day 5: 调整Sprint目标
```

**预案3: Claude API不可用**
```
0-30min: 返回缓存结果
30min-2h: 返回模板回复
2h+: 切换到备用API
```
